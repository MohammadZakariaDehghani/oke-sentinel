# Detections

Six rules over the Kubernetes audit log, each mapped to MITRE ATT&CK, each with
fixtures that prove it fires on what it claims to catch and stays quiet on what
it does not.

The rule definitions live in [`security/detections/`](../security/detections/).
Each file carries the query, the reasoning, the known false positives, and the
fixtures. This page is the overview and the tuning notes.

## Summary

| Rule | Severity | Type | Catches | ATT&CK |
|---|---|---|---|---|
| [`exec-into-pod`](../security/detections/exec-into-pod.yaml) | high | query | `kubectl exec` or `attach` into a running container | [T1609](https://attack.mitre.org/techniques/T1609/), [T1021](https://attack.mitre.org/techniques/T1021/) |
| [`privileged-pod-created`](../security/detections/privileged-pod-created.yaml) | critical | query | Privileged containers, host namespaces, hostPath mounts | [T1611](https://attack.mitre.org/techniques/T1611/), [T1610](https://attack.mitre.org/techniques/T1610/) |
| [`serviceaccount-token-requested`](../security/detections/serviceaccount-token-requested.yaml) | high | query | TokenRequest calls and long-lived token secrets | [T1528](https://attack.mitre.org/techniques/T1528/), [T1078](https://attack.mitre.org/techniques/T1078/) |
| [`rbac-denied-burst`](../security/detections/rbac-denied-burst.yaml) | medium | threshold | Permission enumeration: >10 denials from one identity in 10m | [T1069](https://attack.mitre.org/techniques/T1069/), [T1580](https://attack.mitre.org/techniques/T1580/) |
| [`cluster-admin-binding-created`](../security/detections/cluster-admin-binding-created.yaml) | critical | query | Bindings to `cluster-admin`, and wildcard roles under other names | [T1078](https://attack.mitre.org/techniques/T1078/), [T1098](https://attack.mitre.org/techniques/T1098/) |
| [`secret-enumeration`](../security/detections/secret-enumeration.yaml) | high | threshold | >25 successful secret reads from one identity in 10m | [T1552](https://attack.mitre.org/techniques/T1552/), [T1552.007](https://attack.mitre.org/techniques/T1552/007/) |

## How they fit together

The rules are not six independent alarms. They cover consecutive steps of the
same attack, which is what makes correlating them useful:

```
foothold in a pod
        │
        ├─ rbac-denied-burst ............ what can this token reach?
        │                                 (loud, low severity, earliest signal)
        │
        ├─ secret-enumeration ........... take everything readable
        │                                 (credentials have already left)
        │
        ├─ serviceaccount-token-requested  mint a durable credential
        │
        ├─ cluster-admin-binding-created   grant it everything
        │
        └─ privileged-pod-created ....... escape to the node
           exec-into-pod ................ operate interactively
```

`rbac-denied-burst` is the cheapest and earliest. It fires on the
reconnaissance that precedes everything else, at the cost of being the noisiest.
`cluster-admin-binding-created` is the opposite: nearly silent, and by the time
it fires the cluster is lost. A single rule from this set is a data point; two
of them from the same `user.username` inside an hour is an incident.

## Why the audit log, and what the policy chooses to record

[`security/audit-policy.yaml`](../security/audit-policy.yaml) is not a
catch-everything policy, because that costs more than it is worth and buries
the signal. It makes three kinds of decision:

**Dropped entirely.** Read traffic from the cluster's own components, health
and discovery endpoints, lease renewals, and Events. These are continuous,
enormous, and generated by machines doing exactly what they always do. Without
these drops the audit index is mostly kubelet watches.

**Recorded at `Request` or `RequestResponse`.** Pod creation, RBAC changes,
service account and token operations, exec, admission webhook changes. These
cost more to store because the submitted object is included — and that is the
point. `privileged-pod-created` reads `requestObject.spec.securityContext`; at
`Metadata` level the event would say "someone created a pod" and the rule would
be impossible to write.

**Recorded at `Metadata` only, deliberately.** Secrets and ConfigMaps. Logging
the request body would copy every secret's contents into the audit index, which
is replicated, backed up, and searchable by more people than the secret store
is. `secret-enumeration` needs to know who read what, not what it said.

## Two collection paths, one document shape

This is the part that is easy to get wrong when a detection pipeline moves onto
managed Kubernetes.

On a self-managed control plane you pass `--audit-policy-file` and
`--audit-log-path` to the API server and tail the resulting file. That is what
the kind cluster in CI does, and it is why the pipeline can be tested end to
end on every pull request.

On OKE there is no such flag, because you do not run the API server. Audit
events are delivered to the OCI Audit service, and reaching Elasticsearch means:

```
OCI Audit → Service Connector Hub → OCI Streaming → Filebeat (kafka input) → Elasticsearch
```

That path is created by
[`terraform/modules/oke/audit_export.tf`](../terraform/modules/oke/audit_export.tf)
when `enable_audit_log_export = true`.

Both paths write to the `logs-kubernetes.audit-*` data stream with the same
field names, so every rule here works against either. The rules do not know
which cluster they are running on, and should not.

## Field mappings are part of the detection

The index template in
[`kubernetes/base/ilm/policies.yaml`](../kubernetes/base/ilm/policies.yaml)
maps `user.username`, `objectRef.*`, `responseStatus.code` and a specific
subset of `requestObject` as `keyword`, `integer` or `boolean`.

This is not tidiness. A `text` field cannot be aggregated on, and both threshold
rules aggregate on `user.username`. And a query against a field the index does
not map returns *zero hits rather than an error* — so a typo in a field name
produces a rule that looks like it is working and finding nothing, indefinitely.
`test_every_queried_field_is_mapped` in
[`security/tests/`](../security/tests/) exists entirely to catch that, by
reading the mapping out of the deployed manifest and checking every field every
rule queries.

`requestObject` is mapped `dynamic: false` with explicit properties for the
security-relevant fields. Full fidelity is kept in `_source`, the fields the
rules need are queryable, and an attacker cannot cause a mapping explosion by
submitting an object with ten thousand distinct keys.

## Tuning

**The two thresholds are starting points, not tuned values.** 10 denials in 10
minutes and 25 secret reads in 10 minutes are reasonable defaults for a small
cluster. They are not measurements of anything. Before trusting either, run
this against your own cluster for a week and look at what the normal
distribution actually is:

```json
GET logs-kubernetes.audit-*/_search
{
  "size": 0,
  "query": { "bool": { "filter": [ { "term": { "responseStatus.code": 403 } } ] } },
  "aggs": {
    "per_identity": {
      "terms": { "field": "user.username", "size": 50 },
      "aggs": { "per_hour": { "date_histogram": { "field": "@timestamp", "fixed_interval": "1h" } } }
    }
  }
}
```

Set the threshold above the busiest legitimate identity, then look at that
identity and ask why it is being denied so often — the answer is usually a real
misconfiguration worth fixing.

**Allowlists are blind spots.** Every entry in a `must_not` clause is a
principal the rule will never fire on. They are written as specific service
account names rather than namespace prefixes for that reason: an attacker who
learns that `system:serviceaccount:external-secrets:*` is excluded has been
handed a way to be invisible. Re-read them when someone adds one.

## Deploying and testing the rules

The queries are plain Elasticsearch query DSL. They are deployed as Kibana
**Elasticsearch query** alerting rules, which are available under the Basic
licence on a self-hosted stack — unlike the Security detection engine, which
needs a paid tier. See
[ADR 0001](decisions/0001-eck-operator-vs-helm-vs-managed-opensearch.md) for
the licensing reasoning.

Each rule ships with fixtures, and the tests run in two modes:

```bash
# Structural: field names, mappings, MITRE mapping, documentation coverage.
# No Elasticsearch needed.
pytest security/tests/test_rule_definitions.py

# Behavioural: index the fixtures into a real Elasticsearch, run each rule's
# query, assert it matches every `match` fixture and none of the `no_match`
# ones. Runs in the kind integration job.
ES_URL=https://localhost:9200 pytest security/tests/
```

The behavioural tests build their index from the mapping in the deployed
manifest rather than a copy, so a rule that passes here works against the
cluster's actual mappings.

## What this does not cover

Being clear about the gaps is more useful than implying there are none.

- **No runtime detection.** Everything here comes from the API server. A
  process that spawns inside a container without touching the Kubernetes API —
  a reverse shell from an application vulnerability, cryptomining, lateral
  movement over the pod network — produces no audit event and no alert. That
  needs eBPF-based runtime instrumentation such as Falco or Tetragon, which is
  in the "what I'd add next" section of the README.
- **No network telemetry.** VCN flow logs are not collected, so exfiltration to
  an unusual destination is invisible.
- **Escalation paths not modelled.** `cluster-admin-binding-created` catches
  the direct route. It does not catch escalation via the `escalate` or `bind`
  verbs, or via a controller that will create a binding on an attacker's
  behalf.
- **No alert delivery.** The rules produce alerts in Kibana. Routing them to a
  human — PagerDuty, Slack, an email — is a Kibana connector this project does
  not configure.
- **Thresholds are untuned**, as above.
